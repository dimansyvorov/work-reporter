# Спринтовый отчёт команды (Jira + GitLab)

Локальный или публикуемый веб-отчёт по текущему Jira-спринту: прогресс
направлений, эпики, релизы, списания времени, риски и командная активность.

Сервис сводит разрозненные операционные данные в один снимок для ежедневного
управления спринтом. Jira задаёт план и факт работы, GitLab дополняет картину
MR и коммитами, а все метрики рассчитываются локально. Сервис ничего не меняет
в Jira и GitLab.

## Что это за продукт

Это внутренний read-only dashboard для руководителя кросс-функциональной
команды. Он отвечает не на вопрос «сколько строк кода написано», а на более
практичные вопросы:

- успевает ли команда выполнить спринт и ближайшие релизы;
- где работа остановилась, не оценена или потеряла связь с релизом;
- какое направление или сотрудник перегружены оставшимся объёмом;
- заполнены ли worklog и кому нужно напомнить о недостающих часах;
- что изменилось по задачам вчера и сегодня;
- на каких задачах, эпиках и релизах руководителю нужно сфокусироваться сейчас.

Основная ценность продукта — сократить ручную сверку нескольких Jira-досок,
GitLab-проектов и worklog, раньше обнаруживать риск срыва и давать всей команде
одинаковую картину спринта.

### Для кого и для каких решений

| Роль | Как использует отчёт |
|---|---|
| Руководитель команды / delivery lead | Проводит ежедневный обзор, снимает блокеры, перераспределяет внимание и уточняет объём спринта |
| Лиды направлений | Видят остаток работ, зависшие задачи, нагрузку людей и готовность своего участка |
| Release / product manager | Проверяет готовность версий, отставание от календаря и незакрытые задачи уже выпущенных релизов |
| Команда | Получает прозрачный общий контекст по целям, эпикам, рискам и списаниям |

Типичный цикл использования: автоматический или ручной сбор → обзор сводки,
релизов и рисков → переход в карточку задачи/сотрудника → управленческое действие
в Jira или мессенджере → новый снимок после обновления данных.

### Источники истины

| Источник | Роль в отчёте |
|---|---|
| `team.json` | Бизнес-контур: состав команды, направления, проекты, правила статусов и пороги риска |
| Jira | Обязательный источник спринта, задач, исполнителей, оценок, worklog, эпиков, версий, комментариев и истории статусов |
| GitLab | Необязательное обогащение: MR, коммиты, авторы и вклад в проекты других направлений |
| Корпоративная LLM | Необязательное пояснение уже рассчитанных данных; не является источником фактов |

Подробные определения и ограничения показателей собраны в
[`docs/METRICS.md`](docs/METRICS.md).

## Возможности

- Главная с корректным бизнес-интервалом спринта, health score, рисками и поиском
- Простые вкладки «Главная», «Команда», «Релизы», «Эпики» и «Учёт времени»
- Таймлайн эпиков, карточки релизов и краткая AI-оценка невыпущенных релизов на одну дату
- Компактная матрица списаний всех сотрудников за рабочие дни спринта
- Напоминания о недостающих списаниях с переходом в профиль сотрудника
- Карточки сотрудников, задач и эпиков с деталями Jira/GitLab
- Поиск по отчёту из верхней навигации
- Фильтруемые таблицы рисков, включая задачи без релиза и задачи незакрытых выпусков
- Рейтинги сотрудников, в том числе рейтинг стабильности worklog
- AI-оценка текущего спринта, оценка его прохождения перед завершением и персональные AI-заметки

## Требования

- Python 3.11+
- Доступ к Jira (обязательно) и GitLab (опционально), VPN — если нужен
- Jira-токен и, при включённом GitLab, GitLab-токен в `.env`

## Быстрый старт

```bash
# 1. Зависимости
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 2. Секреты
cp .env.example .env
# заполните JIRA_URL / JIRA_TOKEN и, при необходимости, GITLAB_URL / GITLAB_TOKEN

# 3. Конфиг команды
cp team.json.example team.json
# заполните people, jira.boards/projects, gitlab_projects

# 4. Запуск
python run.py
```

После старта откроется UI (по умолчанию `http://127.0.0.1:8765/`).  
Кнопка **«Обновить данные»** пересобирает отчёт без перезапуска сервера.

### Режимы запуска

| Команда | Что делает |
|---|---|
| `python run.py` | Сбор данных и локальный UI |
| `python run.py --no-collect` | UI на существующем `data/report.json` без нового сбора |
| `python run.py --dump-only` | Сбор и сохранение JSON без UI |
| `python run.py --mock` | Локальное демо без Jira/GitLab |
| `python run.py --reuse-ai` | Сбор с переиспользованием прошлых AI-результатов |
| `python run.py --publish` | Сбор, валидация и публикация |
| `python run.py --publish --reuse-ai` | Публикация нового отчёта без обращений к AI |
| `python run.py --publish-only` | Публикация уже готового `data/report.json` |

Только UI на уже собранном `data/report.json` (без Jira/GitLab и без publish):

```bash
python run.py --no-collect
```

### Демо без API

```bash
python run.py --mock
```

Демо **специально не использует** ваш локальный `team.json` с реальными ФИО.  
Берётся анонимный шаблон `team.json.example` + синтетические задачи/MR.

Если нужно проверить демо на своей структуре направлений — временно подставьте данные в `team.json.example` (без реальных сотрудников) или скопируйте example поверх `team.json` только для локальных экспериментов.

### Только JSON без UI

```bash
python run.py --dump-only
# или
python run.py --mock --dump-only
```

Файлы пишутся в `data/raw.json` и `data/report.json`.

## Основные блоки отчёта

### Сводка спринта и «Настроение команды»

Верхняя сводка сопоставляет прошедшее рабочее время спринта с долей задач,
фактически завершённых после его старта по Jira changelog. Задачи, добавленные
в новый спринт уже закрытыми, не засчитываются как его выполнение.
«Настроение команды» — вычисляемый health score, а не опрос сотрудников:
он объединяет соблюдение плана, темп закрытия задач, риски, готовность релизов и
состояние эпиков. Карточка показывает факторы, которые сильнее всего снижают
оценку. Релизы с датой за пределами текущего спринта не влияют на этот балл.
Рабочее время считается по модели понедельник–пятница без производственного
календаря; в первый день учитывается точное время запуска Jira-спринта, если оно
доступно.

Если в названии спринта есть диапазон вида `03.08.26-14.08.26`, он считается
бизнесовым источником дат. В остальных случаях используется нормализованный
интервал Jira. После окончания интервала UI показывает статус «Завершён», даже
если Jira ещё возвращает техническое состояние `active`.

### Направления и сотрудники

По каждому направлению видны состав, прогресс, оставшиеся задачи, эпики и
техническая активность. Карточка сотрудника объединяет списания по дням,
активные и рисковые задачи, задачи, фактически завершённые после начала спринта,
оставшуюся оценку, нагрузку, события за вчера/сегодня, попадания в рейтинги и
AI-заметку.

Нагрузка сотрудника — прогноз по Jira Remaining Estimate. Задачи без оставшейся
оценки не получают искусственные часы, поэтому при неполных оценках показатель
может быть занижен.

### Эпики и релизы

Таймлайн эпиков показывает вклад направлений, открытые задачи, связь с версиями
и конфликты. Релизные карточки строятся для Jira-версий с датой в окне от начала
спринта до `release_window_days` после его окончания. Риск релиза учитывает
отставание прогресса от календаря, просрочку, Jira `overdue` и приблизительную
нехватку ёмкости.

### Списания времени

Таблица показывает всех сотрудников и все рабочие даты спринта. Дни сгруппированы
по неделям, а на узком экране таблица прокручивается горизонтально. Значения
подсвечиваются по отношению к дневной норме:

- зелёный — норма списана;
- оранжевый — списано меньше нормы;
- красный — списаний нет;
- будущие рабочие дни не считаются нарушением.

Сегодняшний день попадает в напоминание только после завершения нормы рабочего
дня. Кнопка **«Напомнить»** появляется, если за завершённые рабочие дни есть
недостающие часы. Она копирует готовое сообщение в буфер обмена и открывает
`messenger_url` сотрудника в новой вкладке. В сообщение входят дни и недостающие
часы, итог и Markdown-ссылка на страницу отчёта с датой сборки без секунд. Если
кнопка нажата на опубликованной странице, в сообщение попадёт её публичный URL.

Если `messenger_url` пуст, сообщение всё равно копируется, но переход в
мессенджер не выполняется. Ссылка на профиль eXpress имеет вид:

```json
"messenger_url": "https://xlnk.ms/open/profile/USER_UUID"
```

### Риски спринта

Раздел включает таблицы задач, которые могут не закрыться до конца спринта,
застряли, не имеют списаний или оценки, не привязаны к релизу, а также таблицу
**«Релиз выпущен — задача не закрыта»**.

Переключатель **«Релиз вне спринта»** управляет отображением таких задач во всех
таблицах риска. По умолчанию он выключен: Главная показывает риски текущего
спринта, а задачи будущих релизов можно включить вручную. Версии без даты не
считаются штатным сценарием и отдельного переключателя для них нет.

### Рейтинг «Человек-стабильность»

Рейтинг сравнивает списанные часы с уже прошедшим рабочим временем, а не с полной
нормой незавершённого дня. Основную часть балла даёт ровный дневной темп.
Дополнительно учитываются:

- время фактического создания или обновления worklog;
- внесение часов задним числом с настраиваемым льготным сроком;
- часы, списанные раньше реально прошедшего рабочего времени;
- равномерность нескольких записей внутри дня;
- разброс дневного темпа за спринт.

При равном балле выше располагается сотрудник с большим числом задач, которые
перешли в завершающий статус после начала текущего спринта.

Все событийные рейтинги используют единое окно от точного времени начала
спринта до текущего момента. Закрытия берутся из Jira changelog и относятся к
исполнителю на момент перехода; коммиты фильтруются по собственной дате, а не по
дате обновления MR. Уже завершённая задача, добавленная в новый спринт, баллов не
даёт.

Кроме стабильности, отчёт может показывать категории «Коммитёр», «Статист»,
«Эффективность», «Недооценщик», «Переоценщик», «Прогульщик», «Помогальщик» и
сводные «Топы». Негативно звучащие категории включаются только после половины
рабочего времени спринта. Эти показатели предназначены для навигации и
обсуждения, а не для автоматической оценки эффективности сотрудников:
количество задач, часов и коммитов не отражает сложность и бизнес-ценность
работы.

### AI-оценки

Во время обычного сбора корпоративная модель может сформировать:

- общую оценку спринта — только по цели, ключевым задачам и релизам внутри его дат;
- «Оценку прошедшего спринта» по Jira changelog, списаниям, датам и переходам статусов;
- заметки по текущим сотрудникам;
- общую оценку невыпущенных релизов, сгруппированных по дате выпуска.

«Оценка прошедшего спринта» появляется не раньше начала последнего рабочего дня
спринта (`ratings.workday_start_hour`; рабочие дни — понедельник–пятница). Она
ищет возвраты по статусам, поздний старт, смены исполнителя, концентрацию worklog
в конце и незакрытый объём. Для следующего спринта оценка проверяет ближайшие
релизы и приблизительно сопоставляет ключевые темы из их описаний с Jira-задачами.
Неуверенное совпадение так и маркируется, без ложного вывода об отсутствии
задачи. Если Jira ещё не содержит дат следующего спринта, интервал прогнозируется
по длительности текущего и явно называется прогнозным. Отдельные исторические
снимки не сохраняются: анализ выполняется по уже загруженным changelog и worklog.

После появления нового Jira Sprint ID карточка итогов предыдущего спринта не
переносится на Главную. Для выпущенных релизов AI-оценка не генерируется и зелёная
полоса прогресса не рисуется.

Результаты сохраняются в `report.json`; UI не обращается к модели. Если включён
`--reuse-ai`, сетевые обращения к AI полностью пропускаются. Успешные результаты
берутся из предыдущего отчёта только при совпадении Jira Sprint ID, фильтруются
по актуальным сотрудникам и релизам и помечаются в UI как прошлые. Исходное время
генерации сохраняется. При смене спринта или отсутствии предыдущего отчёта сбор
продолжится без AI-блоков.

AI-тексты носят рекомендательный характер. При включении интеграции во внешний
LLM endpoint передаётся подготовленный снимок с рабочим контекстом: в частности,
ФИО, названия и статусы задач, риски, оценки и фрагменты комментариев/worklog,
нужные для релизных оценок. Перед включением проверьте корпоративные правила
обработки данных.

### Публикация на home-server

Сбор на Mac (VPN → Jira/GitLab), на сервер уходит только UI + `report.json`:

```bash
python run.py --publish        # сбор + валидация + выгрузка
python run.py --publish --reuse-ai  # новый сбор без обращений к AI
python run.py --publish-only   # выгрузить уже готовый data/report.json
```

`--reuse-ai` также работает с обычным запуском и `--dump-only`. В локальном
интерфейсе кнопка «Обновить данные» сохраняет выбранный при старте режим.
`--publish-only` и без этого не выполняет сбор и не обращается к AI. Правила
переиспользования описаны в разделе **«AI-оценки»** выше.

Настройки в `.env`:

```bash
PUBLISH_SSH=server
PUBLISH_REMOTE_DIR=/home/USER/path/to/sprint-report
# optional: printed after successful publish
# PUBLISH_PUBLIC_URL=https://your.domain.example/report/
```

`raw.json` на сервер не отправляется и после успешного `--publish` удаляется локально.

### Автопубликация на Mac (VPN + launchd)

LaunchAgent опрашивает раз в **2 минуты**, но публикует не чаще чем раз в **60 минут**, и только в окне **09:00–19:00** (локальное время). Jira/VPN проверяются только когда публикация уже «должна» произойти (прошло ≥60 мин с прошлого успеха). Переопределение: `PUBLISH_EVERY_SEC` в окружении.

```bash
chmod +x scripts/publish-if-vpn.sh scripts/install-launch-agent.sh
./scripts/install-launch-agent.sh
```

- Лог: `~/Library/Logs/work-reporter.log`
- Метка последнего успеха: `~/Library/Logs/work-reporter.last-publish`
- Ручной прогон: `./scripts/publish-if-vpn.sh`
- Снять агент: `launchctl bootout gui/$(id -u)/com.work-reporter.publish && rm -f ~/Library/LaunchAgents/com.work-reporter.publish.plist`

### Telegram-уведомления (только с сервера)

После успешного/неуспешного `--publish` Mac по SSH вызывает скрипт на сервере; **токен Telegram и вызов Bot API только на сервере**.

На сервере: `~/work-reporter-notify/` (шаблон в [`scripts/server-notify/`](scripts/server-notify/)).

В Mac `.env`:

```bash
PUBLISH_NOTIFY_SCRIPT=~/work-reporter-notify/notify-telegram.sh
```

## Конфигурация

| Файл | Назначение | В git? |
|---|---|---|
| `.env` | URL и токены, норма часов, host/port | нет (`.gitignore`) |
| `team.json` | Команда, доски, проекты, пороги метрик | нет (`.gitignore`) |
| `team.json.example` | Анонимный шаблон | да |
| `.env.example` | Шаблон секретов | да |
| `data/` | Кэш сырых данных и отчёта | нет (создаётся при запуске) |

### Что настраивается в `team.json`

Скопируйте `team.json.example` → `team.json` и заполните. Ниже — смысл каждого блока.

#### `directions`

Справочник направлений команды. Порядок ключей = порядок блоков в UI.

| Поле | Пример | Зачем |
|---|---|---|
| `name` | `"Бэкенд"` | Отображаемое имя |
| `short` | `"Бэк"` | Короткое имя в таймлайне эпиков |
| `is_dev` | `true` | Показывать колонку коммитов / dev-метрики |
| `color` | `"#2A53CC"` | Цвет секций эпиков и чипов |

#### `people`

Ростер сотрудников. В отчёт попадают только задачи людей из этого списка.

| Поле | Пример | Зачем |
|---|---|---|
| `name` | `"Иванов Иван Иванович"` | Каноническое ФИО в UI |
| `direction` | `"backend"` | Ключ из `directions` |
| `lead` | `true` | Опционально: лид направления (для AI-рекомендаций) |
| `gender` | `"мужской"` | Опционально: грамматический род для текстов активности |
| `aliases` | `["Ivan Ivanov", "ivan.ivanov"]` | Имена/логины из Jira и GitLab для сопоставления |
| `avatar_url` | `"https://…"` | Явный URL аватара; при сборе копируется локально |
| `avatar_source` | `"jira"` | Предпочтительный источник аватара: `jira` или `gitlab` |
| `jira_username` | `"ivan.ivanov"` | Логин для поиска Jira-профиля и аватара |
| `jira_url` | `"https://…"` | Опциональная явная ссылка на Jira-профиль |
| `gitlab_username` | `"ivan.ivanov"` | Логин для поиска GitLab-профиля и аватара |
| `gitlab_url` | `"https://…"` | Опциональная явная ссылка на GitLab-профиль |

#### `jira`

| Поле | Пример | Зачем |
|---|---|---|
| `projects` | `["DEMO", "OPS"]` | Ключи проектов Jira |
| `boards` | массив досок | Откуда брать спринт/задачи |
| `boards[].id` | `"100"` | Numeric id из URL доски |
| `boards[].name` | `"Основная доска"` | Имя для лога и резервного поиска доски, если id не задан |
| `boards[].primary` | `true` | Основная scrum-доска (окно спринта) |
| `boards[].has_sprints` | `false` | Kanban без Agile sprints |
| `boards[].has_epics` | `true` | Тянуть epic-связи с доски |

Основная доска задаёт имя и даты отчётного спринта. Задачи дополнительных
scrum-досок объединяются с ним, а для kanban-досок берутся открытые задачи,
обновлённые в окне спринта; задачи вне `people` отбрасываются. Если доски не
заданы, сервис пытается найти подходящую Agile-доску по `jira.projects`.

#### `gitlab_projects`

Карта `group/project` → направление (`mobile` / `backend` / …).  
Нужна для MR, коммитов и «помощи другим направлениям» в рейтингах.

#### `status_rules`

Какие статусы для направления считаются `active` / `done` (остальное = other).  
Можно задать `default` и переопределения по ключу направления (`mobile`, `qa`, …).

Это влияет на:
- прогресс направления/эпика/релиза;
- список «осталось»;
- теги риска (неактивность / риск не успеть ставятся только на active).

#### `status_flow`

Опциональный упорядоченный список Jira-статусов. Используется в карточке задачи,
чтобы отличать движение вперёд по процессу от отката. Если поле не задано,
применяется встроенный список распространённых русских и английских статусов.

#### `display_task_filters`

Подстроки в названии задачи. Такие задачи **скрываются из UI-списков** (поддержка/прилёты и т.п.), но могут учитываться в агрегатах.

### Настройка корпоративной AI-модели

AI включён по умолчанию, но фактический вызов выполняется только при наличии URL
и токена. Параметры задаются в `.env`:

```bash
CORP_LLM_ENABLED=1
CORP_LLM_URL=https://llm.example.com/chat/completions
CORP_LLM_TOKEN=...
CORP_LLM_MODEL=/models/Qwen3.6
CORP_LLM_TEMPERATURE=0.2
CORP_LLM_MAX_TOKENS=4096
CORP_LLM_REASONING=off
CORP_LLM_TIMEOUT_SEC=45
CORP_LLM_CACHE_SEC=3000
```

`CORP_LLM_REASONING=off` передаёт в модель
`chat_template_kwargs.enable_thinking=false` и `preserve_thinking=false`.
Значение `on` включает оба флага; неизвестное значение безопасно считается
`off`. По умолчанию reasoning отключён.
Дополнительно ответ очищается от `<think>…</think>`, если шлюз всё же вернул
внутренние рассуждения в обычном поле `content`. `CORP_LLM_MAX_TOKENS`
ограничивает длину ответа модели.

Группы релизов оцениваются независимо. Если часть вызовов завершилась ошибкой,
пакет получает статус `partial`: успешные оценки остаются видимыми, а у
конкретной неоценённой даты UI показывает недоступность вместо общего `ok`.

`CORP_LLM_CACHE_SEC` разрешает повторно использовать недавний результат для
неизменившегося снимка. Чтобы гарантированно не обращаться к модели независимо
от кэша, запускайте сбор с `--reuse-ai`. Полностью отключить AI можно через
`CORP_LLM_ENABLED=0`.

## Как это работает

1. `run.py` выбирает режим: локальный UI, сохранение JSON или публикация.
2. `collector` получает Jira/GitLab либо создаёт mock-данные.
3. Сырые данные сохраняются в `data/raw.json`.
4. Локальный расчёт строит метрики, риски, релизы, профили и рейтинги.
5. AI-блоки генерируются, берутся из кэша или переиспользуются из прошлого отчёта.
6. Готовый снимок сохраняется в `data/report.json`.
7. UI читает `/api/report`; опубликованная версия работает как статический снимок.

Схема ответственности проста: сборщики только получают и нормализуют данные,
`metrics` и `ratings` содержат детерминированные правила, AI-модули добавляют
необязательные интерпретации, а `web/` визуализирует готовый JSON и применяет
только интерактивные фильтры и правила отображения.

`data/raw.json` и `data/report.json` **не коммитятся**: каталог `data/` в `.gitignore`, файлы появляются только при запуске сбора.

## Ограничения интерпретации

- Отчёт — снимок на `meta.fetched_at`, а не real-time представление Jira/GitLab.
- Рабочий календарь считает рабочими только понедельник–пятницу: праздники,
  отпуска, больничные, неполная занятость и индивидуальные графики не загружаются.
- Общий прогресс спринта использует Jira resolution/status category `done`, а
  прогресс направлений — настраиваемые `status_rules`; эти проценты могут
  обоснованно отличаться.
- Метрики качества входных данных зависят от дисциплины Jira: без оценок,
  Remaining Estimate, Fix Version и корректных исполнителей прогнозы неполны.
- Рейтинги и AI-заметки — сигналы для разговора. Их нельзя использовать как
  самостоятельное основание для кадровых или компенсационных решений.

## Замечания по безопасности

- Не коммитьте `.env` и `team.json` — там токены и персональные данные команды.
- `data/` может содержать выгрузки Jira/GitLab с ФИО и задачами.
- `report.json` содержит не только агрегаты, но и карточки задач, worklog,
  комментарии и историю статусов; публикацию нужно защищать как внутренний ресурс.
- `messenger_url` и AI-результаты также могут содержать персональные данные.
- Токены нужны только сборщику и не попадают в публикуемый статический bundle.
- Для публикации репозитория используйте только `*.example` файлы.
