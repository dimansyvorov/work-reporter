# Спринтовый отчёт (GitLab + Jira)

Локальный веб-отчёт по текущему спринту: прогресс направлений, эпики, релизы, списания времени, риски и рейтинги сотрудников.

Данные собираются из Jira (задачи, спринты, worklog, версии) и GitLab (MR/коммиты), считаются локально и открываются в браузере на `localhost`.

## Возможности

- Сводка спринта, настроение команды и прогресс по направлениям
- Таймлайн эпиков, карточки релизов и общая AI-оценка групп релизов на одну дату
- Компактная матрица списаний всех сотрудников за рабочие дни спринта
- Напоминания о недостающих списаниях с переходом в профиль сотрудника
- Карточки сотрудников, задач и эпиков с деталями Jira/GitLab
- Поиск по отчёту и быстрая навигация между разделами
- Фильтруемые таблицы рисков, включая задачи без релиза и задачи незакрытых выпусков
- Рейтинги сотрудников, в том числе рейтинг стабильности worklog
- AI-оценка спринта и персональные AI-заметки по сотрудникам

## Требования

- Python 3.11+ (желательно)
- Доступ к Jira и/или GitLab (VPN, если нужен)
- Токены API в `.env`

## Быстрый старт

```bash
# 1. Зависимости
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 2. Секреты
cp .env.example .env
# заполните GITLAB_URL / GITLAB_TOKEN / JIRA_URL / JIRA_TOKEN …

# 3. Конфиг команды
cp team.json.example team.json
# заполните people, jira.boards/projects, gitlab_projects

# 4. Запуск
python run.py
```

После старта откроется UI (по умолчанию `http://127.0.0.1:8765/`).  
Кнопка **«Обновить данные»** пересобирает отчёт без перезапуска сервера.

### Режимы запуска

| Команда | Что делает |
|---|---|
| `python run.py` | Сбор данных и локальный UI |
| `python run.py --no-collect` | UI на существующем `data/report.json` без нового сбора |
| `python run.py --dump-only` | Сбор и сохранение JSON без UI |
| `python run.py --mock` | Локальное демо без Jira/GitLab |
| `python run.py --reuse-ai` | Сбор с переиспользованием прошлых AI-результатов |
| `python run.py --publish` | Сбор, валидация и публикация |
| `python run.py --publish --reuse-ai` | Публикация нового отчёта без обращений к AI |
| `python run.py --publish-only` | Публикация уже готового `data/report.json` |

Только UI на уже собранном `data/report.json` (без Jira/GitLab и без publish):

```bash
python run.py --no-collect
```

### Демо без API

```bash
python run.py --mock
```

Демо **специально не использует** ваш локальный `team.json` с реальными ФИО.  
Берётся анонимный шаблон `team.json.example` + синтетические задачи/MR.

Если нужно проверить демо на своей структуре направлений — временно подставьте данные в `team.json.example` (без реальных сотрудников) или скопируйте example поверх `team.json` только для локальных экспериментов.

### Только JSON без UI

```bash
python run.py --dump-only
# или
python run.py --mock --dump-only
```

Файлы пишутся в `data/raw.json` и `data/report.json`.

## Основные блоки отчёта

### Списания времени

Таблица показывает всех сотрудников и все рабочие даты спринта. Дни сгруппированы
по неделям, а на узком экране таблица прокручивается горизонтально. Значения
подсвечиваются по отношению к дневной норме:

- зелёный — норма списана;
- оранжевый — списано меньше нормы;
- красный — списаний нет;
- будущие рабочие дни не считаются нарушением.

Сегодняшний день попадает в напоминание только после завершения нормы рабочего
дня. Кнопка **«Напомнить»** появляется, если за завершённые рабочие дни есть
недостающие часы. Она копирует готовое сообщение в буфер обмена и открывает
`messenger_url` сотрудника в новой вкладке. В сообщение входят дни и недостающие
часы, итог и Markdown-ссылка на страницу отчёта с датой сборки без секунд. Если
кнопка нажата на опубликованной странице, в сообщение попадёт её публичный URL.

Если `messenger_url` пуст, сообщение всё равно копируется, но переход в
мессенджер не выполняется. Ссылка на профиль eXpress имеет вид:

```json
"messenger_url": "https://xlnk.ms/open/profile/USER_UUID"
```

### Риски спринта

Раздел включает таблицы задач, которые могут не закрыться до конца спринта,
застряли, не имеют списаний или оценки, не привязаны к релизу, а также таблицу
**«Релиз выпущен — задача не закрыта»**.

Переключатели **«Релиз вне спринта»** и **«Релиз без даты»** управляют
отображением таких задач во всех таблицах риска. По умолчанию оба признака
включены, поэтому сначала виден полный список.

### Рейтинг «Человек-стабильность»

Рейтинг сравнивает списанные часы с уже прошедшим рабочим временем, а не с полной
нормой незавершённого дня. Основную часть балла даёт ровный дневной темп.
Дополнительно учитываются:

- время фактического создания или обновления worklog;
- внесение часов задним числом с настраиваемым льготным сроком;
- часы, списанные раньше реально прошедшего рабочего времени;
- равномерность нескольких записей внутри дня;
- разброс дневного темпа за спринт.

При равном балле выше располагается сотрудник с большим числом закрытых задач.

### AI-оценки

Во время обычного сбора корпоративная модель может сформировать:

- общую оценку спринта;
- заметки по текущим сотрудникам;
- общую оценку релизов, сгруппированных по дате выпуска.

Результаты сохраняются в `report.json`; UI не обращается к модели. Если включён
`--reuse-ai`, сетевые обращения к AI полностью пропускаются. Успешные результаты
берутся из предыдущего отчёта только при совпадении Jira Sprint ID, фильтруются
по актуальным сотрудникам и релизам и помечаются в UI как прошлые. Исходное время
генерации сохраняется. При смене спринта или отсутствии предыдущего отчёта сбор
продолжится без AI-блоков.

### Публикация на home-server

Сбор на Mac (VPN → Jira/GitLab), на сервер уходит только UI + `report.json`:

```bash
python run.py --publish        # сбор + валидация + выгрузка
python run.py --publish --reuse-ai  # новый сбор без обращений к AI
python run.py --publish-only   # выгрузить уже готовый data/report.json
```

`--reuse-ai` также работает с обычным запуском и `--dump-only`. В локальном
интерфейсе кнопка «Обновить данные» сохраняет выбранный при старте режим.
`--publish-only` и без этого не выполняет сбор и не обращается к AI. Правила
переиспользования описаны в разделе **«AI-оценки»** выше.

Настройки в `.env`:

```bash
PUBLISH_SSH=server
PUBLISH_REMOTE_DIR=/home/USER/path/to/sprint-report
# optional: printed after successful publish
# PUBLISH_PUBLIC_URL=https://your.domain.example/report/
```

`raw.json` на сервер не отправляется и после успешного `--publish` удаляется локально.

### Автопубликация на Mac (VPN + launchd)

LaunchAgent опрашивает раз в **2 минуты**, но публикует не чаще чем раз в **60 минут**, и только в окне **09:00–19:00** (локальное время). Jira/VPN проверяются только когда публикация уже «должна» произойти (прошло ≥60 мин с прошлого успеха). Переопределение: `PUBLISH_EVERY_SEC` в окружении.

```bash
chmod +x scripts/publish-if-vpn.sh scripts/install-launch-agent.sh
./scripts/install-launch-agent.sh
```

- Лог: `~/Library/Logs/work-reporter.log`
- Метка последнего успеха: `~/Library/Logs/work-reporter.last-publish`
- Ручной прогон: `./scripts/publish-if-vpn.sh`
- Снять агент: `launchctl bootout gui/$(id -u)/com.work-reporter.publish && rm -f ~/Library/LaunchAgents/com.work-reporter.publish.plist`

### Telegram-уведомления (только с сервера)

После успешного/неуспешного `--publish` Mac по SSH вызывает скрипт на сервере; **токен Telegram и вызов Bot API только на сервере**.

На сервере: `~/work-reporter-notify/` (шаблон в [`scripts/server-notify/`](scripts/server-notify/)).

В Mac `.env`:

```bash
PUBLISH_NOTIFY_SCRIPT=~/work-reporter-notify/notify-telegram.sh
```

## Конфигурация

| Файл | Назначение | В git? |
|---|---|---|
| `.env` | URL и токены, норма часов, host/port | нет (`.gitignore`) |
| `team.json` | Команда, доски, проекты, пороги метрик | нет (`.gitignore`) |
| `team.json.example` | Анонимный шаблон | да |
| `.env.example` | Шаблон секретов | да |
| `data/` | Кэш сырых данных и отчёта | нет (создаётся при запуске) |

### Что настраивается в `team.json`

Скопируйте `team.json.example` → `team.json` и заполните. Ниже — смысл каждого блока.

#### `directions`

Справочник направлений команды. Порядок ключей = порядок блоков в UI.

| Поле | Пример | Зачем |
|---|---|---|
| `name` | `"Бэкенд"` | Отображаемое имя |
| `short` | `"Бэк"` | Короткое имя в таймлайне эпиков |
| `is_dev` | `true` | Показывать колонку коммитов / dev-метрики |
| `color` | `"#2A53CC"` | Цвет секций эпиков и чипов |

#### `people`

Ростер сотрудников. В отчёт попадают только задачи людей из этого списка.

| Поле | Пример | Зачем |
|---|---|---|
| `name` | `"Иванов Иван Иванович"` | Каноническое ФИО в UI |
| `direction` | `"backend"` | Ключ из `directions` |
| `lead` | `true` | Опционально: лид направления (для AI-рекомендаций) |
| `aliases` | `["Ivan Ivanov", "ivan.ivanov"]` | Имена/логины из Jira и GitLab для сопоставления |
| `messenger_url` | `"https://xlnk.ms/open/profile/…"` | Ссылка на профиль/чат для напоминаний; пустая строка отключает переход |

#### `jira`

| Поле | Пример | Зачем |
|---|---|---|
| `projects` | `["DEMO", "OPS"]` | Ключи проектов Jira |
| `boards` | массив досок | Откуда брать спринт/задачи |
| `boards[].id` | `"100"` | Numeric id из URL доски |
| `boards[].primary` | `true` | Основная scrum-доска (окно спринта) |
| `boards[].has_sprints` | `false` | Kanban без Agile sprints |
| `boards[].has_epics` | `true` | Тянуть epic-связи с доски |

#### `gitlab_projects`

Карта `group/project` → направление (`mobile` / `backend` / …).  
Нужна для MR, коммитов и «помощи другим направлениям» в рейтингах.

#### `status_rules`

Какие статусы для направления считаются `active` / `done` (остальное = other).  
Можно задать `default` и переопределения по ключу направления (`mobile`, `qa`, …).

Это влияет на:
- прогресс направления/эпика/релиза;
- список «осталось»;
- теги риска (неактивность / риск не успеть ставятся только на active).

#### `display_task_filters`

Подстроки в названии задачи. Такие задачи **скрываются из UI-списков** (поддержка/прилёты и т.п.), но могут учитываться в агрегатах.

#### `task_tags`

| Поле | По умолчанию | Зачем |
|---|---|---|
| `inactive_days` | `5` | Через сколько дней без updates ставить тег «Неактивная» |

#### `metrics`

Пороги расчёта отчёта:

| Поле | По умолчанию | Зачем |
|---|---|---|
| `release_window_days` | `14` | Релизы: дата в окне `[start спринта … end + N дней]` |
| `slip_tolerance_pp` | `12` | Допуск отставания прогресса задач от календаря релиза (п.п.) |
| `hours_warn_ratio` | `0.5` | Доля от дневной нормы: ниже = «мало списано» |
| `risk_sprint_time_pct` | `70` | После какого % спринта задачи попадают в «риск срыва» |
| `risk_days_left` | `3` | Или если до конца спринта осталось ≤ N дней |
| `stale_days` | `5` | Порог блока «застрявшие» |
| `epic_bar_min_pct` | `28` | Мин. ширина полосы эпика |
| `epic_section_min_pct` | `14` | Мин. ширина секции направления в эпике |
| `risks_limit` | `40` | Сколько рисков отдавать в API |
| `person_tasks_limit` | `40` | Лимит задач в профиле сотрудника |
| `person_active_tasks_limit` | `30` | Лимит active-задач в профиле |

#### `ratings`

| Поле | По умолчанию | Зачем |
|---|---|---|
| `top_n` | `3` | Сколько мест показывать в карточках рейтинга |
| `place_points` | `{1:3,2:2,3:1}` | Очки за места в категории «Топы» |
| `timezone` | `"Europe/Moscow"` | Часовой пояс рабочего дня и времени создания worklog |
| `workday_start_hour` | `9` | Начало рабочего дня; можно задать дробное значение, например `9.5` |
| `worklog_grace_workdays` | `1` | Сколько рабочих дней даётся на внесение worklog без штрафа |
| `advance_tolerance_hours` | `0.5` | Допуск для часов, списанных раньше прошедшего рабочего времени |

#### `ui`

| Поле | По умолчанию | Зачем |
|---|---|---|
| `task_table_preview` | `5` | Сколько строк задач видно до кнопки «Показать ещё» |

#### `gitlab_days`

Fallback-окно GitLab (дни), если у спринта нет даты старта. Можно переопределить env `GITLAB_DAYS`.

### Полезные ключи `.env`

```bash
GITLAB_URL=...
GITLAB_TOKEN=...
JIRA_URL=...
JIRA_TOKEN=...
JIRA_EXPECTED_HOURS_PER_DAY=8
HOST=127.0.0.1
PORT=8765
```

Опционально: `GITLAB_DAYS`, `GITLAB_DIRECTION_MAP` (override карты проектов).

### Настройка корпоративной AI-модели

AI включён по умолчанию, но фактический вызов выполняется только при наличии URL
и токена. Параметры задаются в `.env`:

```bash
CORP_LLM_ENABLED=1
CORP_LLM_URL=https://llm.example.com/chat/completions
CORP_LLM_TOKEN=...
CORP_LLM_MODEL=/models/Qwen3.6
CORP_LLM_TEMPERATURE=0.2
CORP_LLM_TIMEOUT_SEC=45
CORP_LLM_CACHE_SEC=3000
```

`CORP_LLM_CACHE_SEC` разрешает повторно использовать недавний результат для
неизменившегося снимка. Чтобы гарантированно не обращаться к модели независимо
от кэша, запускайте сбор с `--reuse-ai`. Полностью отключить AI можно через
`CORP_LLM_ENABLED=0`.

## Как это работает

1. `run.py` выбирает режим: локальный UI, сохранение JSON или публикация.
2. `collector` получает Jira/GitLab либо создаёт mock-данные.
3. Сырые данные сохраняются в `data/raw.json`.
4. Локальный расчёт строит метрики, риски, релизы, профили и рейтинги.
5. AI-блоки генерируются, берутся из кэша или переиспользуются из прошлого отчёта.
6. Готовый снимок сохраняется в `data/report.json`.
7. UI читает `/api/report`; опубликованная версия работает как статический снимок.

`data/raw.json` и `data/report.json` **не коммитятся**: каталог `data/` в `.gitignore`, файлы появляются только при запуске сбора.

## Структура репозитория

```
run.py                      # режимы запуска, локальный сервер и публикация
team.json.example           # анонимный шаблон команды
.env.example                # шаблон секретов и настроек окружения
src/collector.py            # сценарий сбора и сохранения отчёта
src/metrics.py              # метрики, риски, релизы и профили
src/ratings.py              # рейтинги сотрудников
src/ai_brief.py             # AI-оценка спринта
src/ai_person_notes.py      # AI-заметки по сотрудникам
src/ai_release_briefs.py    # AI-оценки групп релизов
src/ai_reuse.py             # безопасное переиспользование прошлых AI-результатов
web/                        # статический интерфейс отчёта
data/                       # локальные runtime-данные
```

## Замечания по безопасности

- Не коммитьте `.env` и `team.json` — там токены и персональные данные команды.
- `data/` может содержать выгрузки Jira/GitLab с ФИО и задачами.
- `messenger_url` и AI-результаты также могут содержать персональные данные.
- Для публикации репозитория используйте только `*.example` файлы.
