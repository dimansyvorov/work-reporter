# Метрики и правила интерпретации

Этот документ фиксирует бизнес-смысл показателей спринтового отчёта. Он нужен,
чтобы одинаково трактовать цифры в UI и понимать, какие данные влияют на выводы.

## Область расчёта

- Отчёт строится вокруг одного Jira-спринта. Его имя и цель берутся с основной
  scrum-доски. Если имя содержит явный диапазон `dd.mm.yy-dd.mm.yy`, этот диапазон
  является бизнесовым источником дат; иначе используются даты Jira. При
  отсутствии scrum-спринта используется доступный fallback через Jira.
- В командные метрики попадают только задачи, чей исполнитель сопоставлен с
  участником `people` в `team.json`. Сопоставление использует каноническое ФИО и
  `aliases`.
- Дополнительные scrum- и kanban-доски расширяют набор задач, но не меняют окно
  основного спринта.
- Jira — обязательный источник фактов. При отключённом GitLab отчёт сохраняет
  спринтовые, релизные и worklog-показатели, но не показывает полноценные
  MR/commit-метрики.
- Все показатели относятся к моменту `meta.fetched_at`. После изменения Jira или
  GitLab нужен новый сбор.
- Бизнесовые даты спринта, релизов и общих показателей считаются в обязательном
  числовом `server_timezone` из `team.json`. Персональные рабочие даты используют
  `people[].timezone`, а при его отсутствии — серверное смещение. Оба значения —
  абсолютные смещения от UTC.
- Если эпик попал в отчёт только через задачу релиза и Jira вернула в Epic Link
  один ключ, названия всех таких эпиков восстанавливаются одним пакетным Jira
  Search-запросом. Ключ используется как заголовок только при недоступности
  метаданных самого эпика.

## Статусы и прогресс

### Общий прогресс спринта

`Выполнение задач = задачи, завершённые внутри окна спринта и остающиеся Jira-done / все задачи команды в области отчёта × 100%`.

Момент завершения определяется по Jira changelog. Текущее состояние дополнительно
проверяется по `resolution` или Jira status category `done`, поэтому повторно
открытая задача не остаётся выполненной. Уже закрытые до старта задачи выводятся
отдельным числом и не увеличивают выполнение нового спринта.

`Прохождение спринта = прошедшие рабочие часы / все рабочие часы × 100%`.

Рабочими считаются понедельник–пятница, праздничный календарь не загружается.
Дневная граница берётся из `ratings.workday_start_hour`, длительность — из нормы
часов Jira; для первого дня используется точное Jira `startDate`, если оно
приходится на бизнесовую дату начала. Граница Jira `endDate`, приходящаяся ровно
на полночь, трактуется как исключающая: последним днём спринта считается
предыдущая дата. После последней даты бизнес-статус принудительно становится
«Завершён», даже если Jira ещё возвращает `active`.

### Прогресс направления

Для направлений статус классифицируется через `status_rules`:

- `active` — работа ещё лежит на данном направлении;
- `done` — направление свою часть завершило;
- `other` — задача существует, но не участвует в active/done-прогрессе этого
  направления.

Поэтому общий процент спринта и процент конкретного направления могут
различаться. Например, задача в `Ready for testing` может быть завершена для
разработки, но ещё не быть закрыта в Jira.

`display_task_filters` скрывает служебные задачи из пользовательских списков и
AI-снимков. Такие задачи всё ещё могут участвовать в части агрегатов, поэтому это
не инструмент исключения данных из расчёта.

## Метки задач

| Метка | Условие |
|---|---|
| Fix Version | Информационная метка каждой Jira-версии задачи; сама по себе не является риском |
| Без релиза | Active-задача без Fix Version, если она не скрыта `display_task_filters` |
| Задержка | У незавершённой задачи в поле Sprint обнаружен текущий и ещё один предыдущий/другой спринт |
| Неактивная | Active-задача не обновлялась не меньше `task_tags.inactive_days` |
| Риск не успеть | Remaining Estimate задачи больше ёмкости до конца спринта: рабочие дни × дневная норма |

Проверка «Риск не успеть» использует оценку одной задачи и стандартную дневную
норму. Она не знает об отпусках, параллельных задачах и индивидуальной
доступности, поэтому является ранним сигналом, а не обещанием срока.
Завершённые задачи сохраняют информационные метки Fix Version, но не получают
операционные риски и не подсвечиваются как рисковые в модалках.

## Риски спринта

В таблицах риска рассматриваются незакрытые в Jira задачи команды; задачи,
скрытые `display_task_filters`, не показываются.

| Таблица | Правило попадания |
|---|---|
| Могут не закрыться | Спринт прошёл порог `risk_sprint_time_pct` или осталось не больше `risk_days_left`, а задача ещё не Jira-done |
| Застряли | С даты последнего обновления прошло не меньше `metrics.stale_days` |
| Открыты без списаний | В поздней фазе спринта по задаче нет ни одного worklog в окне отчёта |
| Без оценки | Нет положительного Original Estimate |
| Без релиза | Нет Fix Version |
| Релиз выпущен — задача не закрыта | Хотя бы одна Fix Version имеет `released=true`, а задача не Jira-done |

Переключатель «Релиз вне спринта» — UI-фильтр. Он не пересчитывает риски, а
скрывает/показывает соответствующие строки и по умолчанию выключен. Отдельного
режима для версии без даты нет: это считается ошибкой исходных данных.

## Списания времени

- Дневная норма задаётся `JIRA_EXPECTED_HOURS_PER_DAY`.
- Рабочими днями считаются понедельник–пятница. Производственный календарь,
  праздники, отпуска и индивидуальные графики не загружаются.
- В матрице завершённого рабочего дня: `ok` — не меньше нормы, `warn` — есть
  положительное списание ниже нормы, `bad` — списаний нет.
- Ожидание для текущего дня растёт от `ratings.workday_start_hour` до полной
  дневной нормы. Будущие дни не считаются нарушением.
- Напоминание формируется по завершённым рабочим дням с недостающими часами.
  Текущий день включается только после того, как прошла полная дневная норма.

Дата `started`, текущий день и начало рабочего дня определяются в персональном
часовом поясе сотрудника. Если `people[].timezone` отсутствует, используется
`server_timezone`. Поэтому один и тот же момент может относиться к разным
календарным дням у сотрудников, а «Сегодня», ожидаемые часы и напоминания
рассчитываются для каждого отдельно.

Worklog суммируются по дате `started`, а своевременность записи определяется по
`created`/`updated`. Это позволяет отличить день, за который списано время, от
момента фактического внесения записи.

`metrics.hours_warn_ratio` используется в персональном worklog-сигнале и
контексте AI-заметок, но не меняет цвета дневных ячеек матрицы.

## Нагрузка сотрудника

Нагрузка — forward-looking оценка активной тарелки:

`нагрузка % = сумма положительных Remaining Estimate активных задач /
max(0, ёмкость всего спринта − уже списанные часы) × 100%`.

`ёмкость всего спринта = рабочие дни спринта × дневная норма`.

Интерпретация уровня:

- меньше 80% — `ok`;
- 80–110% — `tight`;
- больше 110% — `over`;
- нет доступной ёмкости — `unknown`;
- нет активных задач — `empty`.

Задача с отсутствующим или нулевым Remaining Estimate добавляет 0 часов. UI
показывает количество таких задач; чем их больше, тем менее полон прогноз.

## Релизы

В релизные карточки попадают неархивные Jira-версии с `releaseDate` в диапазоне:

`[начало спринта; конец спринта + metrics.release_window_days]`.

Версия без `releaseDate` считается некорректной для процесса и не получает
релизную карточку. Сборщик не создаёт для неё искусственную дату.

Прогресс релиза — доля задач версии, завершённых по `status_rules` их направлений.
В расчёт попадают задачи версии, назначенные участникам команды.

Для выпущенной версии (`released=true`) UI показывает статус и числа задач, но не
рисует зелёную полосу прогресса и не запрашивает отдельную AI-оценку.

Релиз получает риск, если выполняется хотя бы одно условие:

- дата прошла, а active-задачи остались;
- прогресс задач отстаёт от календарного прогресса более чем на
  `slip_tolerance_pp` процентных пунктов;
- сумма active-оценок больше приблизительной ёмкости до даты релиза;
- Jira пометила версию `overdue`.

Календарный прогресс релиза считается от старта спринта до `releaseDate`.
Приблизительная ёмкость равна `рабочие дни до релиза × дневная норма × число
исполнителей с active-задачами`. Для задачи без положительного Original Estimate
в релизном агрегате используется условная единица в 1 час, поэтому перегрузка —
ориентир для проверки данных, а не точный capacity plan.

## Эпики

Таймлайн объединяет задачи эпика по направлениям и связывает эпик с Jira-
версиями. Для эпиков рассчитываются прогресс, открытый объём, доля связи с
релизами и конфликты: несколько невыпущенных версий, близкие окна релизов,
рисковые задачи, длинный возраст эпика и active-задачи уже выпущенной версии.

В компоненте «Эпики в спринте» health score учитываются только эпики, у которых
есть задачи текущего спринта. Вне-спринтовые задачи не увеличивают этот риск.

## «Настроение команды»

Это детерминированный sprint health score от 0 до 100, а не эмоциональный опрос.
Он объединяет пять оценок, каждая также лежит в диапазоне 0–100:

| Компонент | Базовый вес | Смысл |
|---|---:|---|
| Соблюдение плана | 0,28 | Разрыв между прошедшим рабочим временем и долей задач, завершённых внутри окна спринта |
| Темп закрытия | 0,14–0,30 | Темп завершений по Jira changelog; вес растёт к концу, а в первые 20% используется нейтральная стартовая база |
| Здоровье задач | 0,24 | Доли задач под риском, без активности, списаний, оценки или релиза |
| Готовность релизов | 0,20 | Доля невыпущенных релизов внутри дат спринта без риска и среднее отставание прогресса |
| Эпики в спринте | 0,10 | Прогресс только задач текущего спринта относительно рабочего времени; текущие риски и переносы учитываются раздельно |

Перед выводом веса нормализуются и округляются так, чтобы их сумма оставалась
равной 100%. В начале спринта итог приближается к нейтральным 66 баллам, чтобы
отсутствие накопившихся рисков не выглядело как уже достигнутый успех. Модалка
показывает исходный балл, полноту данных, коэффициент и величину поправки.
Влияние каждого драйвера рассчитывается через потерю соответствующего компонента
с учётом его веса, а не отдельной эвристической шкалой.

Временная шкала использует рабочие часы понедельника–пятницы, точное время старта
Jira-спринта и дневную норму. Производственные праздники не загружаются. Факт
выполнения берётся из переходов Jira changelog внутри окна спринта; уже закрытая
до старта задача показывается отдельно и не увеличивает выполнение нового
спринта. Для эпиков и прогресс, и риск считаются только по задачам текущего
спринта. Тег переноса из другого спринта является отдельным слабым сигналом и не
приравнивается к неактивности, отсутствию релиза или угрозе срока.

Будущие релизы и связанные только с ними задачные риски не снижают числовую
оценку текущего спринта.

## AI-область и оценка завершения

- AI-оценка текущего спринта получает только релизы с `releaseDate` внутри
  бизнес-интервала спринта, их описания, ключевые темы и задачи. Будущие релизы
  исключены из её фактов и рекомендаций.
- Релизная AI-оценка строится только для невыпущенных версий и не требует
  фиксированного набора заголовков: первое предложение содержит вердикт, дальше
  остаются только существенные факты и действия.
- Для всех AI-оценок, затрагивающих релизы, плановая дата считается полным
  календарным днём. Невыпущенная версия в этот день получает подготовленные
  признаки `phase=release_day`, `publication_expected_this_evening=true` и
  `publication_overdue=false`: штатный выпуск ожидается вечером после рабочего
  дня. Риски задач при этом сохраняются как оценка готовности к вечернему окну,
  но не доказывают просрочку публикации. `publication_overdue=true` появляется
  только со следующего календарного дня.
- «Оценка прошедшего спринта» доступна с `ratings.workday_start_hour` последнего
  рабочего дня. Производственный календарь не загружается: рабочими считаются
  понедельник–пятница.
- Детерминированный код предварительно разбирает Jira changelog, worklog, даты и
  переходы статусов. Модель получает уже подготовленные аномалии, результаты
  релизов, прогнозный или фактический интервал следующего спринта и приблизительное
  сопоставление тем из описаний релизов с задачами.
- При неуверенном текстовом совпадении вывод обязан говорить, что тему не удалось
  уверенно сопоставить. Отдельная история рассчитанных рисков по Sprint ID не
  сохраняется; источником истории остаётся Jira changelog.
- При смене Sprint ID итоговая карточка прошлого спринта исчезает.

## Рейтинги

Рейтинг показывает `ratings.top_n` мест и полный список по клику.

Для событий используется единое окно: точное время начала спринта — текущее
время, но не позднее его окончания. Текущий статус задачи сам по себе не даёт
баллов. Завершение определяется по переходу Jira changelog в done-статус
направления, а результат относится к исполнителю на момент перехода. Задачи,
которые попали в новый спринт уже завершёнными, в рейтинг не входят.

| Категория | Как считается |
|---|---|
| Человек-стабильность | 65% — близость ежедневных часов к уже прошедшему рабочему времени сотрудника; 35% — дисциплина внесения worklog; дополнительно штрафуется разброс дневного темпа. Дата, своевременность, ритм и «Наперёд» считаются в `people[].timezone` с fallback на `server_timezone` |
| Коммитёр | Число уникальных repository commits из всех веток настроенных проектов с `committed_date` внутри окна спринта по автору коммита; дубликаты удаляются по паре `проект + SHA` |
| Статист | Число переходов в done-статус направления внутри окна спринта |
| Эффективность | Сумма Original Estimate завершённых в окне задач / часы worklog спринта; минимум 4 часа списаний |
| Недооценщик | Сумма часов сверх Original Estimate по задачам текущего спринта в любом статусе; карточка показывает количество таких задач и превышение в часах |
| Переоценщик | Сумма часов между Original Estimate и положительным worklog по завершённым в окне задачам; карточка также показывает количество таких задач |
| Прогульщик | Наименьшая сумма worklog в спринте |
| Помогальщик | Repository commits автора с `committed_date` внутри окна спринта в проектах не своего направления |
| Топы | Очки за призовые места по схеме `ratings.place_points` |

### Своевременность списаний в «Человеке-стабильности»

Вклад своевременности — 70% дисциплины, то есть 24.5 балла из 100 итогового
рейтинга. За каждый час начисляется коэффициент:

- `1` — внесён в дату работ;
- `0.9` — внесён после даты работ, но не позднее
  `ratings.worklog_grace_workdays` рабочих дней (по умолчанию один);
- `0` — внесён после льготного срока.

Коэффициенты усредняются по часам, не по количеству worklog. Поэтому если все
часы внесены на следующий рабочий день, своевременность равна 90%, а итоговый
рейтинг ниже на 2.45 балла относительно тех же часов, внесённых день в день,
при прочих равных. Разбиение одной записи на несколько этот штраф не меняет.
При допуске `0` следующий день сразу получает `0`; при увеличенном допуске
мягкий коэффициент `0.9` применяется ко всему настроенному льготному сроку.

Дата работ берётся из `started`, момент внесения — из `max(created, updated)`,
если известен хотя бы один из этих timestamp. Оба момента переводятся в часовой
пояс сотрудника. Рабочие дни — понедельник–пятница, без производственного
календаря: внесение за пятницу в субботу, воскресенье или понедельник попадает
в срок следующего рабочего дня. Правки существующего worklog, как и раньше,
могут сдвинуть момент внесения по `updated`.

В `stability.recording_timing` передаются часы и их доли по фактическому сроку:
`same_day`, `next_workday` (включая выходные до него), `later` и
`before_workday`. Это разбивка дат, а не коэффициентов: при нестандартном
увеличенном допуске часть `later` ещё может получать мягкий штраф. Записи до
даты работ не считаются задержкой, но сохраняют отдельный штраф «Наперёд» и
не входят в «День в день». Записи без известных timestamp не входят в
знаменатель долей; при полном отсутствии таких данных разбивка равна `null`.

UI называет взвешенный показатель «Своевременность» (в карточке — «сроки») и
показывает фактическую разбивку отдельно. Нерассчитанная «Равномерность» скрыта,
но её существующий вклад в формулу не меняется: `null` по-прежнему нейтрален
и даёт полный вклад этого компонента. Рассчитанные `0%` видны и продолжают
влиять на балл. Вес дневного темпа, штраф за разброс и превышение дневной нормы,
допуск «Наперёд» и порядок сортировки не изменены.

### Остальные правила рейтингов

«Недооценщик», «Переоценщик» и «Прогульщик» включаются после половины рабочего
времени спринта: учитываются только понедельник–пятница и уже прошедшая часть
текущего рабочего дня. У «Человека-стабильности» и «Эффективности» при равенстве
выше участник с большим числом задач, завершённых внутри окна спринта.

У «Недооценщика» основная сортировка идёт по суммарному превышению оценки, при
равенстве — по количеству задач. «Переоценщик» сортируется симметрично: сначала
по суммарным часам ниже оценки, затем по количеству завершённых задач. Компактный
формат карточек: `N задач · +X ч` и `N задач · -X ч` соответственно.

Рейтинги чувствительны к гранулярности задач, правилам оценки, алиасам авторов и
дисциплине заполнения Jira. Они помогают находить темы для разговора, но не
измеряют ценность человека и не должны использоваться как автоматическая HR-
оценка.

## AI-блоки

AI формирует пояснение к уже рассчитанному снимку: оценку текущего спринта,
итоговую оценку его прохождения, персональные заметки и оценку невыпущенных
релизов, сгруппированных по дате. UI не вызывает модель и не пересчитывает эти
данные.

AI-вывод может ошибаться и не меняет фактические показатели. При включённой
интеграции в настроенный LLM endpoint отправляется подготовленный рабочий
контекст, включая персональные данные, названия/статусы задач и, для релизного
анализа, ограниченные фрагменты комментариев или worklog. Используйте эту
функцию только в разрешённом корпоративном контуре.

## Главные ограничения

- Нет интеграции с календарём отсутствий и праздников.
- Система не знает фактическую сложность, качество результата и бизнес-ценность
  задачи.
- Коммиты и MR зависят от принятого Git workflow и качества сопоставления
  Jira-ключей/авторов.
- Неполные Original/Remaining Estimate и Fix Version делают прогнозы нагрузки и
  релизов неполными.
- Опубликованная версия — статический снимок; свежесть всегда проверяется по
  времени сборки.
